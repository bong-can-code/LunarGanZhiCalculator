# 03. 결과 영속화 + 공유 URL + 동적 OG 이미지 (바이럴 루프)

> 우선순위: 🟡 중간 · 예상 규모: 2~3d · 위험: 중간 · 사용자 액션: DB·개인정보 정책 결정 (필수)

## 배경

- 현재 궁합 결과는 **100% 클라이언트에만 존재** → 친구에게 "우리 궁합 이거 봐" 하고 **링크를 못 보내고 이미지만** 공유 가능.
- 바이럴 서비스의 확산 루프는 보통 `결과 생성 → 공유 URL → 링크 받은 사람이 그 결과를 보고 → 자기도 해봄`. 이 루프의 "공유 URL"과 "링크별 맞춤 미리보기(동적 OG)"가 없음.
- 02번(정적 OG)의 상위 단계: 저장된 결과가 있어야 결과별 동적 OG 이미지를 만들 수 있음.

## 목표

궁합 결과를 서버에 저장하고 `/r/{id}` 공유 URL을 발급한다. 그 URL은 결과별 동적 OG 이미지(점수·등급·두 캐릭터)를 노출해, 링크만으로 확산되게 한다.

## 설계 결정 (사용자 협의 필요)

### A. 저장소
- **권장**: Railway PostgreSQL 애드온 + SQLAlchemy. 관리형이라 운영 부담 적음.
- 대안: SQLite(파일) — Railway 컨테이너는 재배포 시 파일이 날아갈 수 있어(임시 파일시스템) 부적합. 볼륨 마운트 필요.
- → **Postgres 권장**.

### B. 동적 OG 이미지 생성 방식 (택1)
1. **클라이언트 업로드형 (권장·간단)**: 이미 `gunghap.js`가 캔버스로 1080×1080 카드를 만듦. 결과 저장 시 이 PNG를 함께 서버에 올려 저장 → OG 이미지로 그대로 서빙. 서버 렌더링 불필요, 캐릭터 재구현 불필요.
2. **서버 렌더형**: 서버에서 Pillow(+cairosvg로 SVG→PNG) 또는 headless 브라우저로 매번 렌더. 캐릭터 SVG 포팅 필요, 의존성 무거움. → 비권장.
- → **1번(클라이언트 업로드형) 권장**. 단 업로드 검증(크기·형식·용량 제한) 필요.

### C. 개인정보 처리 (⚠️ 법적 검토 포인트)
- 저장 대상에 **이름·생년월일시·성별**이 포함되면 개인정보. 한국 개인정보보호법 고려 필요.
- 선택지:
  - (a) **최소 저장**: 계산 결과(점수·등급·띠·지역·이미지)만 저장하고 **원본 생일/이름은 저장 안 함** → 개인정보 최소화. 공유엔 충분.
  - (b) 원본까지 저장(재계산·수정 지원) → 동의·보관기간·파기 정책 필요.
- → **(a) 최소 저장 권장**. 공유 카드에 이름을 넣더라도 "표시용 닉네임"으로 취급하고 민감정보(생일)는 미저장.

## 작업 항목

- [ ] 저장소 선택 확정(위 A) 및 Railway Postgres 프로비저닝
- [ ] 스키마: `results(id, created_at, score, grade, person1_json, person2_json, districts_json, image_key)` — person_json은 표시용 최소 필드만
- [ ] 짧은 공유 ID 생성(예: base62 8자리, 추측 어렵게)
- [ ] `POST /gunghap/calculate` 결과에 `share_id` 포함 + 저장
- [ ] 이미지 저장: 캔버스 PNG 업로드 엔드포인트 or 결과 저장 시 함께 전송. 저장 위치: DB blob(작은 규모) or Railway 볼륨/오브젝트 스토리지
- [ ] `GET /r/{id}`: 저장된 결과를 렌더하는 페이지 + 결과별 OG 메타(`og:image`=저장 이미지, `og:title`=`"OO×OO 궁합 56점"`)
- [ ] 공유 버튼이 이미지뿐 아니라 `/r/{id}` **링크도** 공유하도록 확장
- [ ] 만료/정리 정책(예: 90일 후 파기) 배치 or on-read TTL
- [ ] 봇/OG 크롤러가 `/r/{id}` 접근 시 JS 없이도 메타태그 보이도록 서버사이드 렌더 확인

## 내가(사용자) 할 일

1. **저장소 승인**: Railway Postgres 애드온 추가에 동의(무료 티어 한도·초과 시 과금 정책 확인). 내가 `railway add`로 붙일 수 있으나 **인프라 변경/과금 가능성**이라 사전 동의 필요.
2. **개인정보 정책 결정**: 위 C의 (a) 최소저장 / (b) 원본저장 중 선택. (a) 권장.
   - (b) 선택 시: 개인정보 처리방침 페이지·수집 동의 UI·보관기간을 정해야 함(내가 초안 작성 가능).
3. **보관기간(TTL) 결정**: 공유 결과를 며칠 보관할지(예: 90일).
4. (선택) 공유 URL에 노출될 문구/디자인 방향.

## 검증 방법

- 결과 생성 → `share_id` 발급 → `/r/{id}` 재접속 시 동일 결과 렌더 확인.
- `curl -A "facebookexternalhit" /r/{id}`로 OG 메타가 서버응답에 포함되는지 확인(JS 없이).
- 페이스북/트위터/카카오 디버거로 결과별 카드 미리보기.
- 만료 정책 동작 테스트.
- pytest: 저장/조회/만료 로직 단위 테스트.

## 리스크

- 중간. DB 도입으로 상태·마이그레이션·백업 관리 필요.
- 개인정보 저장은 법적 리스크 → **최소 저장 원칙**으로 완화.
- 이미지 저장 용량 증가 → 만료 정책·용량 상한 필요.
