# 04. Kakao 장소 API 캐싱 + 레이트리밋 (비용·안정성)

> 우선순위: 🟢 낮음 · 예상 규모: 0.5~1d · 위험: 낮음 · 사용자 액션: Kakao 키 발급

## 배경

- `GET /gunghap/places`가 매 요청마다 Kakao 로컬 API를 직접 호출(식당 5 + 카페 5 = 요청당 2콜).
- Kakao 로컬 검색 무료 쿼터는 **일 100,000건** 수준. 바이럴로 트래픽이 몰리면 소진 위험 → 소진 시 전원 폴백으로 떨어짐.
- 구별 검색 결과는 자주 바뀌지 않으므로 **캐싱에 매우 적합**(예: 24시간 TTL).
- 현재 레이트리밋이 없어 특정 IP의 남용/과도 호출을 못 막음.

## 목표

Kakao 호출을 캐싱해 쿼터 소모를 크게 줄이고, 간단한 레이트리밋으로 남용을 방지한다.

## 작업 항목

- [ ] 구(district) 단위 응답 캐싱(식당/카페 각각). TTL 예: 6~24시간
  - 저장소: 인메모리(`functools.lru_cache` + 만료 래퍼) → 단일 프로세스면 충분 / 다중 워커·인스턴스면 Redis 고려(03의 DB나 Railway Redis 애드온)
- [ ] 캐시 히트/미스 로깅으로 실제 절감률 측정
- [ ] `/gunghap/places`에 IP 기반 간단 레이트리밋(예: 분당 N회) — `flask-limiter` 또는 경량 자체 구현
- [ ] Kakao 호출 타임아웃·재시도·부분실패 처리 점검(현재 5초 타임아웃 + 폴백은 이미 있음)
- [ ] 쿼터 임계 접근 시 자동으로 폴백 전환하는 안전장치(선택)

## 내가(사용자) 할 일

1. **Kakao REST API 키 발급**: [Kakao Developers](https://developers.kakao.com) → 애플리케이션 생성 → REST API 키 확보. (로컬 API는 별도 승인 없이 사용 가능하나 앱 등록 필요)
2. **Railway에 키 등록 동의**: 발급한 키를 프로덕션 환경변수로 설정.
   - 방법: `railway variables --set KAKAO_REST_API_KEY=발급키` (프로덕션 변경이라 사전 동의 필요) → 자동 재배포됨.
   - 키가 없으면 지금처럼 구별 대표 명소 폴백으로 계속 동작(오류 없음).
3. (다중 인스턴스로 확장 시) Redis 애드온 추가 여부 결정.

## 검증 방법

- 같은 구를 여러 번 호출 → 2번째부터 Kakao 미호출(캐시 히트) 확인(로그).
- 레이트리밋 초과 시 429 응답 + 사용자에게 친절한 안내.
- 키 설정 후 실제 식당·카페가 뜨는지, 키 제거 시 폴백으로 정상 전환되는지 확인.

## 리스크

- 낮음. 캐싱·레이트리밋은 부가 레이어라 실패해도 폴백으로 수렴.
- 인메모리 캐시는 워커/인스턴스별로 분리됨 → 규모 커지면 공유 캐시(Redis) 필요.
