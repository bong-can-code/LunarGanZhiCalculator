# 01. 절기 계산 캐싱 (성능)

> 우선순위: 🔴 높음 · 예상 규모: 0.5d · 위험: 낮음 · 사용자 액션: 없음

## 배경 (측정 근거)

- `calculate_saju` 1회당 `solar_term_datetime`를 **83회** 호출.
- 단일 사주(대운 포함) **33ms/req**, 궁합(2명) **65ms/req**.
- `solar_term_datetime(year, longitude)`는 입력이 같으면 결과가 항상 같은 **순수 함수**인데, 매 요청마다 하루 단위 스캔(~365회) + 이분법 60회를 새로 계산.
- `functools.lru_cache` 프로토타입 실험 결과: **33ms → 1.9ms (약 17배)**.

바이럴 트래픽이 몰리면 gunicorn 동기 워커가 이 CPU 계산으로 블로킹되므로, 캐싱이 안정성에도 직결된다.

## 목표

절기 절입시각 계산을 캐싱해 요청당 계산량을 제거하고, 프로세스 재시작에도 견디도록 사전계산 테이블 옵션을 검토한다.

## 작업 항목

- [x] `saju/solar_terms.py`의 `solar_term_datetime`에 `functools.lru_cache(maxsize=None)` 적용
  - 인자가 `(int, float)`라 해시 가능 → 바로 적용됨
- [x] 캐시가 모듈 전역이므로, `pillars.py`/`luck.py`가 `from .solar_terms import solar_term_datetime`로 가져가는 참조도 동일 캐시를 공유하는지 확인 → import 방식상 동일 함수 객체라 자동 공유됨(코드 변경 불필요)
- [x] 벤치마크 재측정해 개선 수치를 기록 (아래 결과 참고)
- [ ] ~~(선택) 사전계산 워밍업/JSON 테이블~~ → **건너뜀**. 최악의 경우(요청마다 새 연도)도 5.69ms로 충분히 빨라 불필요하다고 판단.

- 벤치마크 결과(동일 프로세스 내 반복 측정):
